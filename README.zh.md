# DocAlchemy

> 一份文档进来，每个分析引擎对它的理解，归一化后在同一个地方可视化对比。

## 为什么做这个？

文档分析很难让人放心。今天，任何需要搞清楚一份文档*实际包含什么*的人——挑选 OCR 引擎的工程团队、搭建数据摄取流水线的数据团队、对比提取质量的研究者——都不得不面对一个**没有统一语言**的引擎生态。

每个引擎（Docling、MinerU、Surya 等）都有自己的输出格式、自己的坐标系、自己对"块"、"表格"、"阅读顺序"的定义。评估哪怕一个引擎，都意味着对着原始 JSON 发呆、写一次性脚本、靠截图对比。用同一份文件比较两个引擎，就是把这些事情做两遍，然后在脑子里拼凑结论。那个真正的问题——*哪个引擎真正读懂了这份文档？*——从来没有干净的答案。

### 连严谨的 benchmark 也回答不了

公开 benchmark 已经越来越认真了。[OmniDocBench](https://github.com/opendatalab/OmniDocBench)（CVPR 2025）在约 1,650 份真实 PDF 上评测五项解析任务——文本 OCR、表格结构、公式还原、布局检测、阅读顺序——涵盖十种文档类型，配有专家人工标注，支持按语言、扫描质量、版式复杂度分维度拆解。它设计严谨、经过同行评审，是目前最好的同类工作。

但它仍然回答不了你的问题，原因有四：

**你的文档不在里面。** Benchmark 的数据集是固定的。你的合同、发票、研究报告、内部文件——都不在其中。基于约 1,650 份精选页面的聚合分数，对你流水线里今天这份文档没有任何具体意义。

**聚合分数掩盖了真正的失败。** 表格 TEDS = 0.78，可能意味着所有表格都差不多，也可能意味着简单表格 0.95、复杂跨列表格 0.30。对你最重要的失败，恰恰是被平均值稀释掉的那些。

**指标和可用性之间有鸿沟。** 归一化编辑距离和树编辑距离衡量的是与 ground truth 的字符级和结构相似度。它们不衡量提取出来的 markdown 够不够让 LLM 正常推理，也不衡量提取出来的表格能不能不经手工清洗直接导入数据库。"NED 分数高"和"能在我的流水线里用"之间的距离可以很大。

**数字看不出错在哪里。** Benchmark 告诉你表格提取得了 0.82 分。它不告诉你引擎把第 3 列和第 4 列合并了。把提取出来的表格画在原始页面上，一眼就能看出来。

OmniDocBench 回答的是：*哪个引擎在一组学术策划文档上整体更好？*
DocAlchemy 回答的是：*哪个引擎在这份具体文档上更好，我能看到为什么吗？*

### 什么能替代排行榜

核心思路是**一个提供商无关的文档分析检视层**。上传一份源文档，让任意多个分析引擎处理它。DocAlchemy 保存每个引擎的原始输出，把它们全部归一化到同一个稳定 schema，然后把结果作为覆盖层渲染在**原始文档**上——源 PDF 始终是视觉基准，每个引擎都在同一条基线上接受评判。

这很重要，因为版式和结构质量*首先是定性的*。你可以读一百份关于表格提取的 benchmark 指标，但仍然不知道某个引擎有没有在第 4 页合并两列。把引擎提取出来的表格画在原表上，一秒钟就能看出来。DocAlchemy 把"相信这个提取结果"从一次信仰跳跃，变成了一件可以用眼睛验证的事。

简言之：文档分析行业没有一块中立的地方，能让人看清楚各个引擎实际做了什么——只有把真相抹平的排行榜。DocAlchemy 建立这块地方：一个稳定的渲染契约，每个提供商隔离且可替换，源文档始终居于中心，你的眼睛是最终裁判。

## 快速开始

### 前置依赖

| 工具 | 用途 |
|------|------|
| Docker & Docker Compose | 提供商 worker 容器及基础设施（PostgreSQL、Redis） |
| Python ≥ 3.11 + [PDM](https://pdm.fming.dev) | 后端依赖管理 |
| Node.js + [pnpm](https://pnpm.io) | 前端依赖管理 |

### 启动

```bash
# 1. 克隆并进入仓库
git clone https://github.com/Priestch/docalchemy.git
cd docalchemy

# 2. 复制并编辑环境配置
cp .env.example .env

# 3. 安装 Python 和 Node 依赖
make install

# 4. 执行数据库迁移
make migrate

# 5. 启动所有服务
make dev
```

`make dev` 会在 Docker 中启动 PostgreSQL 和 Redis，重新构建并启动每个提供商
worker 容器，然后拉起 Litestar 后端和 Vite 开发服务器。

```
后端：  http://localhost:8000
前端：  http://localhost:5173
```

停止所有服务：`make dev-stop`

### 提供商 Worker

每个分析引擎在独立的 Docker 容器中运行。首次启动时，容器会下载并缓存模型权重到
`./cache/` 目录下——每个提供商可能需要几 GB 空间，耗时较长。后续启动会复用缓存。

```bash
make dev-workers          # 不重新构建镜像，直接启动 worker
make dev-workers-rebuild  # 重新构建镜像后启动 worker
```

### 常用命令

| 命令 | 说明 |
|------|------|
| `make dev` | 启动所有服务 |
| `make dev-stop` | 停止所有服务 |
| `make dev-infra` | 仅启动 PostgreSQL 和 Redis |
| `make dev-backend` | 仅启动后端 |
| `make dev-frontend` | 仅启动前端开发服务器 |
| `make migrate` | 执行数据库迁移 |
| `make test` | 运行测试 |
| `make lint` | 运行代码检查 |

## 它做什么

- **一次摄取。** 上传单份源文档；它作为每次分析的不可变视觉基准被存储。
- **运行多个引擎。** 把同一份源文档分发给多个分析提供商——目前有 Docling、MinerU、Surya、OpenDataLoader 和 FrankenOCR；更多引擎通过稳定契约接入。
- **归一化到同一 schema。** 每个提供商的原生输出被转换为应用自有的 `RenderDocument` schema——统一坐标系、统一块模型、统一渲染方式。前端永远看不到提供商原生 JSON。
- **在真实文档上检视。** 把归一化后的块、表格、阅读顺序、图像作为覆盖层渲染在原始 PDF 上，质量直接对照源文档目测——而不是对照排行榜。查看器基于 [document-viewer](https://github.com/Priestch/document-viewer) 构建，这是同一作者维护的开源 PDF 查看 SDK。
- **追踪每次运行。** 提供商名称、版本、配置、延迟和原始产物都为每次分析记录在案，结果可复现。

## 如何组织

DocAlchemy 是一个务实 DDD 风格的 Python 后端（Litestar）加 React/Vite 查看器，提供商运行时通过单一契约隔离在外。

- **摄取** — 文件上传和源存储。
- **编排** — 提供商选择、任务下发（Celery）、重试和运行状态追踪。
- **提供商运行时** — 每个引擎在自己的隔离环境中运行，拥有独立依赖，通过提供商契约对外。
- **归一化与渲染** — 将提供商输出转换为 `RenderDocument` schema 并提供给查看器。

保持整体一致的唯一规则：**应用拥有一个稳定的渲染 schema。** 提供商来了又去；schema——以及基于它构建的查看器——保持不变。

## 基于 document-viewer

检视体验——渲染源 PDF 并在上面绘制归一化提供商覆盖层——基于 [**document-viewer**](https://github.com/Priestch/document-viewer) 构建，这是同一作者维护的开源 PDF 查看 SDK。DocAlchemy 既是该 SDK 的用户，也是一个展示：当一个查看器被当作文档智能的*检视工具*而非单纯的渲染器来对待时，它可以成为什么。
